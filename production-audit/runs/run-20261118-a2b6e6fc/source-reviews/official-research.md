## 1. `java-25-concurrency`

**Official URL** — <https://docs.oracle.com/en/java/javase/25/> · JLS SE 25 ch. 17 <https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html> · virtual threads <https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html> · JEP 505 <https://openjdk.org/jeps/505>
**Version** — Java SE 25 / JDK 25. JEP 444 virtual threads are the JDK 25 baseline; **JEP 505 StructuredTaskScope is Release 25, Status *Closed/Delivered*, but is a preview API.**

**The rule.** JLS §17.4.5: *"When a program contains two conflicting accesses that are not ordered by a happens-before relationship, it is said to contain a data race."* JLS §17.4.3: *"If a program has no data races, then all executions of the program will appear to be sequentially consistent."* JLS §17.5: *"A thread that can only see a reference to an object after that object has been completely initialized is guaranteed to see the correctly initialized values for that object's final fields"* and *"final fields also allow programmers to implement thread-safe immutable objects without synchronization."* Atomicity (`java.util.concurrent.atomic.AtomicInteger`, Java SE 25 javadoc): *"An `int` value that may be updated atomically"*; `compareAndSet` *"Atomically sets the value to `newValue` if the current value `== expectedValue`"*. Virtual threads: *"A virtual thread cannot be unmounted during blocking operations when it is pinned to its carrier. A virtual thread is pinned when it runs a `native` method or a foreign function … Pinning does not make an application incorrect, but it might hinder its scalability."* JFR: *"`jdk.VirtualThreadPinned` indicates that a virtual thread was pinned (and its carrier thread wasn't freed) for longer than the threshold duration. This event is enabled by default with a threshold of 20 ms."* JEP 505: *"To use the `StructuredTaskScope` API you must enable preview APIs"* — `javac --release 25 --enable-preview`, `java --enable-preview`.

**This repository.** Java 25 (`pom.xml:34-36`). Safe publication uses j.u.c atomics, not non-final mutable fields: `product-service/src/main/java/com/shop/productservice/security/ServiceTokenProvider.java:30` (`AtomicReference<CachedToken> cache`) with a `ReentrantLock` at `:31`; same pattern at `rating-service/.../ServiceTokenProvider.java:29`, `media-service/.../ServiceTokenProvider.java:30`, `order-service/.../ServiceTokenProvider.java`, `search-service/.../ServiceTokenProvider.java`. Counter: `product-service/src/main/java/com/shop/productservice/service/ProductMetrics.java:21,26` (`AtomicInteger`). Virtual threads are **off** by default: `utils/common-spring/src/main/resources/application.yml:9-11` (`spring.threads.virtual.enabled: ${VIRTUAL_THREADS_ENABLED:false}`). Monitor-based synchronization exists in main code and would pin a carrier: `order-service/src/main/java/com/shop/orderservice/service/OrderReconciliationScheduler.java:203,214`, `order-service/src/main/java/com/shop/orderservice/service/OrderCommitCoordinator.java:101`, `search-service/src/main/java/com/shop/searchservice/security/ServiceTokenProvider.java:46`. `StructuredTaskScope` is used nowhere.

**Decision.** Baseline Java 25. (1) Any mutable shared state must be published through a j.u.c atomic or an explicit lock — the repo complies. (2) No new code may use `StructuredTaskScope`: it is preview-only in JDK 25 and would require `--enable-preview` at compile *and* run time; the repo correctly avoids it. (3) Virtual threads stay disabled by default; the three monitor-based critical sections must be converted to j.u.c primitives before `VIRTUAL_THREADS_ENABLED` can be turned on. (4) Keep the default-on `jdk.VirtualThreadPinned` (20 ms) JFR event in the production profile.

**Risks.** Pinning a carrier serialises unrelated requests — invisible in code review. Preview APIs break the build the moment the flag is not propagated to every module and to the runtime image.

## 2. `spring-bean-scopes`

**Official URL** — <https://docs.spring.io/spring-framework/reference/core/beans/factory-scopes.html>
**Version** — Spring Framework 7.0.x reference (the project resolves **7.0.9** via the Spring Boot 4.1.1 BOM: `spring-boot-dependencies-4.1.1.pom` → `<spring-framework.version>7.0.9</spring-framework.version>`).

**The rule.** *"Only one shared instance of a singleton bean is managed, and all requests for beans with an ID or IDs that match that bean definition result in that one specific bean instance being returned by the Spring container."* *"The singleton scope is the default scope in Spring."* Because that one instance serves every caller, it is shared across request threads and must therefore be thread-safe. Prototype: *"a new bean instance every time a request for that specific bean is made … As a rule, you should use the prototype scope for all stateful beans and the singleton scope for stateless beans."* and *"In contrast to the other scopes, Spring does not manage the complete lifecycle of a prototype bean … configured destruction lifecycle callbacks are not called. The client code must clean up prototype-scoped objects."* Request/session/application/websocket scopes are *"available only if you use a web-aware Spring ApplicationContext"*, otherwise *"an IllegalStateException that complains about an unknown bean scope is thrown."* *"A thread scope is available but is not registered by default."*

**This repository.** 151 `@Component`/`@Service`/`@Repository` classes under `*/src/main` are default singletons; no `@RequestScope`/`@SessionScope`/`@ApplicationScope` anywhere. **One singleton violates the stateless rule:** `product-service/src/main/java/com/shop/productservice/job/ProductMediaSweepJob.java:27` declares `private int currentPage = 0;` and mutates it at `:40` and `:42` inside the `@Scheduled` method at `:29`. Prototype scope is used in exactly five places, all stateless builders: `product-service/.../config/MediaClientConfig.java:33-37`, `rating-service/.../config/RestClientConfig.java:61`, `media-service/.../config/ProductClientConfig.java:57`, `search-service/.../config/ProductClientConfig.java:38`, `order-service/.../config/RestClientConfig.java:83`. Configuration is injected into singletons through **non-final `@Value` fields**: `product-service/.../service/OutboxRelay.java:35,38,41,44` and `rating-service/.../outbox/RatingOutboxRelay.java:31,34,37,40`.

**Decision.** Every bean here is a singleton and must be stateless or thread-safe. Request/session/application scope is banned (stateless microservices; `utils/common-spring/src/main/resources/application.yml:94` `stateless-session: true`). Prototype scope is permitted only for stateless, resource-free objects. `ProductMediaSweepJob.currentPage` must be removed or replaced by an `AtomicInteger`/local variable. Configuration must move to final constructor-injected fields so the singleton's state is final and safely published under JLS §17.5.

**Risks.** A prototype that owns a connection or thread leaks silently (no destruction callback). A single mutable `int` in a `@Scheduled` bean is a latent lost update the moment the scheduler is multi-threaded (or virtual-threaded).

## 3. `spring-transactions`

**Official URL** — <https://docs.spring.io/spring-framework/reference/data-access/transaction.html> (7.0 pages `declarative/annotations.html`, `declarative/tx-propagation.html`, `declarative/rolling-back.html`, `event.html`)
**Version** — Spring Framework **7.0.9** (Boot 4.1.1).

**The rule.** *"In proxy mode (which is the default), only external method calls coming in through the proxy are intercepted. This means that self-invocation (in effect, a method within the target object calling another method of the target object) does not lead to an actual transaction at runtime even if the invoked method is marked with `@Transactional`."* *"transactional methods in interface-based proxies must always be public and defined in the proxied interface."* Defaults: *"The propagation setting is PROPAGATION_REQUIRED."* … *"Any RuntimeException or Error triggers rollback, and any checked Exception does not."* REQUIRED + inner rollback-only ⇒ *"A corresponding UnexpectedRollbackException is thrown at that point."* REQUIRES_NEW: *"always uses an independent physical transaction … This may lead to exhaustion of the connection pool and potentially to a deadlock … Do not use PROPAGATION_REQUIRES_NEW unless your connection pool is appropriately sized, exceeding the number of concurrent threads by at least 1."* NESTED: *"works only with JDBC resource transactions."* After-commit: *"`@TransactionalEventListener` … the listener is bound to the commit phase of the transaction by default"*; *"If no transaction is running, the listener is not invoked at all … you can, however, override that behavior by setting the `fallbackExecution` attribute."*

**This repository.** No self-invocation of a `@Transactional` method and no `@Transactional` on a private method (verified by a full scan of `*/src/main`). `Propagation.REQUIRED` at `rating-service/.../service/RatingEventService.java:40` and `media-service/.../outbox/MediaEventService.java:32`. `REQUIRES_NEW` at `payment-service/.../service/PaymentWriter.java:26`, `order-service/.../service/CompensationFailureService.java:36`, `order-service/.../service/impls/IdempotencyServiceImpl.java:105`, and via `TransactionTemplate` at `order-service/.../service/impls/OrderServiceImpl.java:120` and `order-service/.../service/impls/IdempotencyServiceImpl.java:45`. **Pool-size rule is live:** Hikari `maximum-pool-size` default 20 at `utils/common-spring/src/main/resources/application.yml:15`, while virtual threads are switchable on (`:9-11`). **Rollback-rule deviation:** `order-service/.../service/impls/OrderServiceImpl.java:445` declares `@Transactional(noRollbackFor = BusinessException.class)` and `BusinessException extends RuntimeException` (`utils/common-core/src/main/java/com/shop/common/core/exception/BusinessException.java:6`), so it suppresses the documented default rollback for a runtime exception. `PROPAGATION_NESTED` unused (correct for the JPA provider). After-commit side effects are implemented manually at `inventory-service/src/main/java/com/shop/inventoryservice/service/InventoryCacheService.java:25-36` (`TransactionSynchronizationManager.registerSynchronization(...afterCommit())`, falling back to an immediate eviction when no transaction is active — the documented equivalent of `@TransactionalEventListener(AFTER_COMMIT, fallbackExecution = true)`); `@TransactionalEventListener` is not used anywhere.

**Decision.** `@Transactional` only on externally-invoked methods; self-invocation banned (enforced by a static test); never on a private method. Keep the default rollback rule — the single `noRollbackFor` must be removed or justified. Every `REQUIRES_NEW` must be justified against the documented pool budget (pool size > concurrent threads by ≥ 1). `NESTED` banned. External side effects registered as after-commit work; the `InventoryCacheService` pattern is the canonical implementation. `UnexpectedRollbackException` must not be swallowed.

**Risks.** `REQUIRES_NEW` inside an outer transaction holds the outer connection while the inner transaction needs a second one — with 20 connections and >19 concurrent outer transactions this deadlocks, and enabling virtual threads removes the natural ceiling that currently hides it. `noRollbackFor` on a runtime exception commits whatever was already written.

## 4. `spring-boot-4`

**Official URL** — <https://docs.spring.io/spring-boot/reference/> (serves **4.1.2** stable; the `/spring-boot/4.1/...` path redirects here) — `features/external-config.html`, `features/developing-auto-configuration.html`; migration notes: <https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide>
**Version** — Spring Boot 4.1.x reference; the project pins `spring-boot-starter-parent` **4.1.1** (`pom.xml:9-12`).

**The rule.** *"Spring Boot uses a very particular PropertySource order … Later property sources can override the values defined in earlier ones."* *"The properties that map to `@ConfigurationProperties` classes … are public API but the accessors (getters/setters) of the class itself are not meant to be used directly"*; *"We recommend that `@ConfigurationProperties` only deal with the environment and, in particular, does not inject other beans from the context."* *"Auto-configurations must be loaded only by being named in the imports file."* *"If your configuration needs to be applied in a specific order, you can use the `before`, `beforeName`, `after` and `afterName` attributes on the `@AutoConfiguration` annotation or the dedicated `@AutoConfigureBefore` and `@AutoConfigureAfter` annotations."* *"the order in which auto-configuration classes are applied only affects the order in which their beans are defined. The order in which those beans are subsequently created is unaffected."* *"we recommend using only `@ConditionalOnBean` and `@ConditionalOnMissingBean` annotations on auto-configuration classes."* Migration: *"To clarify the scope of `spring-boot-starter-aop`, it has been renamed to `spring-boot-starter-aspectj`."* *"Spring Boot now uses Jackson 3 as its preferred JSON library. Jackson 3 uses new group IDs and package names with `com.fasterxml.jackson` becoming `tools.jackson`. … For libraries that require Jackson 2, dependency management for Jackson 2 remains and a Jackson 2 ObjectMapper can be used alongside Boot's auto-configuration for Jackson 3 if needed."* Starter table: Spring Web MVC → `spring-boot-starter-webmvc`; *"All test 'starter' POMs are named `spring-boot-starter-<technology>-test`"* and *"you don't need to define this starter anymore."*

**This repository.** Auto-configuration is compliant: six modules ship `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`; every class is `@AutoConfiguration`; documented ordering attributes are used at `utils/common-spring/src/main/java/com/shop/common/spring/autoconfigure/WebAutoConfiguration.java:16` (`after = I18nAutoConfiguration.class`) and `.../TracingAutoConfiguration.java:29` (`before = OpenTelemetryTracingAutoConfiguration.class`); only `@ConditionalOnClass`/`@ConditionalOnMissingBean`/`@ConditionalOnProperty` are used. Deviations are listed in [§20](#20-version-applicability-findings): the pinned `spring-boot-starter-aop` 4.0.0-M2 (`pom.xml:73`, `pom.xml:188-189`, used at `utils/common-logging/pom.xml:25`), three `spring-boot-starter-web` usages (`utils/common-spring/pom.xml:47`, `utils/common-security/pom.xml:43`, `order-service/pom.xml:38`), redundant `spring-boot-starter-test` next to per-technology test starters, and the half-migrated Jackson 2/3 split (`utils/common-spring/src/main/java/com/shop/common/spring/autoconfigure/Jackson2ObjectMapperAutoConfiguration.java:10-18`; the offline dependency tree of `utils/common-spring` shows **both** `com.fasterxml.jackson.core:jackson-databind:2.21.5` and `tools.jackson.core:jackson-databind:3.1.5` on the compile classpath, while 93 source files still import `com.fasterxml.jackson` — e.g. `rating-service/.../RatingEventService.java:69` serialises the outbox payload — and only `gateway-service` is on Jackson 3, e.g. `gateway-service/src/main/java/com/shop/gateway/filter/GatewayErrorResponseWriter.java:8-9`).

**Decision.** Auto-configuration stays in the `.imports` files and is never component-scanned. `@ConfigurationProperties` types read only the Environment. Replace `spring-boot-starter-aop` 4.0.0-M2 with `spring-boot-starter-aspectj` at the Boot-managed version (the repo *does* use `@Aspect`: `AuditAspect`, `LoggerAspect`). Migrate the three `spring-boot-starter-web` usages to `spring-boot-starter-webmvc`. Drop the redundant explicit `spring-boot-starter-test`. Close the Jackson split deliberately — one generation only, or an explicit, documented Jackson 2 side-car with an explicitly configured `ObjectMapper` (the current bare `new ObjectMapper().registerModule(new JavaTimeModule())` is not equivalent to Boot's auto-configured mapper).

**Risks.** Renaming the AOP starter changes the transitive dependency set of every module. Switching to `spring-boot-starter-webmvc` changes the managed Jackson starter and therefore the MVC mapper, which changes response serialisation for 93 call sites. A half-migrated Jackson setup makes the REST layer and the outbox/Kafka layer produce different JSON.

## 5. `spring-kafka`

**Official URL** — <https://docs.spring.io/spring-kafka/reference/kafka.html> → `kafka/annotation-error-handling.html`
**Version** — Spring for Apache Kafka **4.1.x** (stable 4.1.2 served; the project resolves `spring-kafka` **4.1.1** from the Boot 4.1.1 BOM). Broker `apache/kafka:3.9.0` (`docker-compose.yml:69`).

**The rule.** *"The error handler can recover (skip) a record that keeps failing. By default, after ten failures, the failed record is logged (at the ERROR level)."* *"Using a `FixedBackOff` with `FixedBackOff.UNLIMITED_ATTEMPTS` causes (effectively) infinite retries."* *"The default recoverer logs the failed record after retries are exhausted. You can use a custom recoverer, or one provided by the framework such as the `DeadLetterPublishingRecoverer`."* Default back off is *"the default configuration (`FixedBackOff(0L, 9)`)"*. *"If the recoverer fails (throws an exception), the failed record will be included in the seeks."* *"The `DefaultErrorHandler` considers certain exceptions to be fatal, and retries are skipped for such exceptions; the recoverer is invoked on the first failure."* *"Non-Blocking Retries (the `@RetryableTopic` annotation) are NOT supported with batch listeners."*

**This repository.** `utils/common-kafka/src/main/java/com/shop/common/kafka/consumer/BaseKafkaListenerConfig.java:42-48` has two branches: with a template it builds a `DeadLetterPublishingRecoverer` (`:43`) + `new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3L))` (`:44`); **without a template it builds `new DefaultErrorHandler(new FixedBackOff(1000L, 3L))` (`:46`) — no recoverer**, so the record is only logged and then skipped. **`product-service/src/main/java/com/shop/productservice/kafka/MediaLifecycleListenerConfig.java:18-28` builds its own factory and never calls `setCommonErrorHandler`** — also no recoverer, no DLT. Services that do use the shared factory with a template: `product-service/.../RatingLifecycleListenerConfig.java:16-19`, `notification-service/.../NotificationListenerConfig.java:17-20`, `shipping-service/.../ShippingListenerConfig.java:17-20`. The replay tooling depends on the recoverer: `utils/common-kafka/src/main/java/com/shop/common/kafka/replay/DeadLetterReplayService.java:25-27` reads the `kafka_dlt-original-*` headers that `DeadLetterPublishingRecoverer` adds, wired at `utils/common-kafka/src/main/java/com/shop/common/kafka/config/KafkaAutoConfiguration.java:54-61`. `@RetryableTopic` is not used anywhere and no container is a batch listener.

**Decision.** Every listener factory sets an explicit `CommonErrorHandler` with a bounded `BackOff` and an explicit `DeadLetterPublishingRecoverer`. The no-template branch (`BaseKafkaListenerConfig.java:46`) is removed and the two-argument constructor (`:28-30`) is banned in production code. `MediaLifecycleListenerConfig` must extend `BaseKafkaListenerConfig`. The retry budget stays `FixedBackOff(1000L, 3L)`; `UNLIMITED_ATTEMPTS` is banned. `PoisonRecordException` (`utils/common-kafka/.../consumer/BaseKafkaConsumer.java:71`) must be classified not-retryable so it reaches the DLT on the first failure. `@RetryableTopic` is not adopted.

**Risks.** The log-only default recoverer is silent data loss: the record is skipped and its offset committed, so neither the business flow nor the DLQ replay tooling ever sees it. A DLT publish failure causes redelivery with the back off reset, which can become an infinite loop during a DLT outage.

## 6. `kafka-guarantees`

**Official URL** — <https://kafka.apache.org/documentation/> (the top-level index is client-rendered; the versioned canonical pages used are <https://kafka.apache.org/39/configuration/producer-configs/>, <https://kafka.apache.org/39/configuration/consumer-configs/> and <https://kafka.apache.org/39/design/design/>)
**Version** — Apache Kafka **3.9** documentation, matching the broker image `apache/kafka:3.9.0` (`docker-compose.yml:69`). Client side the project resolves `kafka-clients` **4.2.1** from the Boot 4.1.1 BOM (`<kafka.version>4.2.1</kafka.version>`).

**The rule.** `acks`: *"acks=0 … No guarantee can be made that the server has received the record"*; *"acks=1 … should the leader fail immediately after acknowledging the record but before the followers have replicated it then the record will be lost"*; *"acks=all This means the leader will wait for the full set of in-sync replicas to acknowledge the record. This guarantees that the record will not be lost as long as at least one in-sync replica remains alive. This is the strongest available guarantee. … Note that enabling idempotence requires this config value to be 'all'."* `enable.idempotence`: *"When set to 'true', the producer will ensure that exactly one copy of each message is written in the stream. If 'false', producer retries due to broker failures, etc., may write duplicates … enabling idempotence requires `max.in.flight.requests.per.connection` to be less than or equal to 5 … `retries` to be greater than 0, and `acks` must be 'all'."* `transactional.id`: *"If no TransactionalId is provided, then the producer is limited to idempotent delivery. … By default the TransactionId is not configured, which means transactions cannot be used. Note that, by default, transactions require a cluster of at least three brokers."* `transaction.timeout.ms`: *"The maximum amount of time in milliseconds that a transaction will remain open before the coordinator proactively aborts it. … Default: 60000 (1 minute)."* Scope of exactly-once (Design, Message Delivery Semantics): *"Kafka supports exactly-once delivery in Kafka Streams, and the transactional producer/consumer can be used generally to provide exactly-once delivery when transferring and processing data between Kafka topics. Exactly-once delivery for other destination systems generally requires cooperation with such systems … Otherwise, Kafka guarantees at-least-once delivery by default."*

**This repository.** `utils/common-kafka/src/main/java/com/shop/common/kafka/config/KafkaProperties.java:61-73` satisfies every documented idempotence precondition: `acks = "all"` (`:108`), `enable.idempotence = true` (`:111`), `max.in.flight.requests.per.connection = 1` (`:66`, ≤ 5), `retries = 3` (`:109`, > 0). The service config repeats `acks: all` / `retries: 3` at `product-service/src/main/resources/application.yml:38-40`. **No `transactional.id` is set anywhere** ⇒ the producer is limited to idempotent delivery and Kafka transactions cannot be used; the exactly-once effect for the database write is obtained with the transactional outbox instead. `retries = 3` is a deliberate reduction from the broker default `2147483647`, with the outer bound at `product-service/src/main/resources/application.yml:74` (`max-retries: 10`). Consumer properties (`KafkaProperties.java:75-82`) leave `isolation.level` at the default `read_uncommitted` — harmless today, a trap if a transactional producer is ever added. The dev broker is single-node with `KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1` (`docker-compose.yml:85`).

**Decision.** Keep `acks=all` + `enable.idempotence=true` + `max.in.flight ≤ 5`. Do **not** set `transactional.id`; therefore this system makes **no** exactly-once claim about Kafka, and the audit states explicitly that Kafka's exactly-once guarantee does not extend to the PostgreSQL write — that effect comes from the outbox plus idempotent consumers. `retries=3` plus the outbox `max-retries` form a bounded two-level budget. If a transactional producer is introduced, `isolation.level=read_committed` must be set on every consumer and the broker must have ≥ 3 nodes.

**Risks.** `acks=all` still loses a record if every ISR fails. `retries=3` is far below the broker default, pushing failures onto the outbox path. `read_uncommitted` is a latent trap. Transactions on the single-node dev broker fail at coordinator creation, not at the first send.

## 7. `postgres-locking`

**Official URL** — <https://www.postgresql.org/docs/current/explicit-locking.html> (version-pinned pages used: <https://www.postgresql.org/docs/16/explicit-locking.html>, <https://www.postgresql.org/docs/16/sql-select.html>)
**Version** — PostgreSQL **16** documentation (16.16 at retrieval), matching `postgres:16-alpine` (`docker-compose.yml:30`).

**The rule.** *"FOR UPDATE causes the rows retrieved by the SELECT statement to be locked as though for update. This prevents them from being locked, modified or deleted by other transactions until the current transaction ends."* *"Row-level locks are released at transaction end or during savepoint rollback, just like table-level locks."* Locking clause: *"To prevent the operation from waiting for other transactions to commit, use either the NOWAIT or SKIP LOCKED option. … With SKIP LOCKED, any selected rows that cannot be immediately locked are skipped. Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table."*

**This repository.** The canonical queue-consumer pattern is implemented through JPA: `product-service/src/main/java/com/shop/productservice/repository/OutboxEventRepository.java:22-26` — `@Lock(LockModeType.PESSIMISTIC_WRITE)` + `@QueryHint(name = "jakarta.persistence.lock.timeout", value = "-2")` (the JPA skip-locked sentinel) over `… WHERE e.status = :status AND e.id = (SELECT MIN(e2.id) …)`. Same pattern at `rating-service/.../outbox/OutboxEventRepository.java:22,32`, `media-service/.../outbox/OutboxEventRepository.java:25,35`, `shipping-service/.../outbox/OutboxEventRepository.java:22,32`, `payment-service/.../outbox/OutboxEventRepository.java:22,30`, `order-service/.../repository/OutboxEventRepository.java:23,33`, `promotion-service/.../repository/OutboxEventRepository.java:23,36`, `inventory-service/.../repository/OutboxEventRepository.java:23,31`. The claim runs in its own short transaction at `product-service/.../service/OutboxRelay.java:67-68`, so the lock is released at commit before the Kafka publish at `:95`; the final-state update re-locks at `:137` inside another short transaction at `:117`; stranded claims are recovered by the lease-based UPDATE at `:126` and `OutboxEventRepository.java:35-46`. **Decision.** `SKIP LOCKED` is used **only** for the outbox claim and the outbox final-state update — the documented queue-like case. The claim transaction stays short and commits before any external call. **The claim must not resolve a single `MIN(id)` row**, because with `SKIP LOCKED` a busy row makes the claim return nothing while lower-ranked rows are free; it must select an ordered candidate set (`ORDER BY id LIMIT n`). `notification-service findRetryCandidates` must declare an explicit lock timeout and skip the contended row instead of failing the whole page. Every `SKIP LOCKED` usage is paired with the existing lease/reclaim mechanism.

**Risks.** With a single-`MIN(id)` claim, two relay instances cannot both progress on the same pending set — claim throughput is effectively serialised. `SKIP LOCKED` on the final-state update silently leaves a row in `SENDING` until the lease expires, which delays the "sent" state and can cause a duplicate publish. The JPA→PostgreSQL mapping of the `-2` sentinel is provider behaviour and must be proven by a test, not assumed.

## 8. `postgres-isolation`

**Official URL** — <https://www.postgresql.org/docs/current/transaction-iso.html> (version-pinned: <https://www.postgresql.org/docs/16/transaction-iso.html>, <https://www.postgresql.org/docs/16/ddl-constraints.html>)
**Version** — PostgreSQL **16** documentation, matching `postgres:16-alpine`.

**The rule.** *"Read Committed is the default isolation level in PostgreSQL."* *"two successive SELECT commands can see different data, even though they are within a single transaction."* Update semantics: *"the second updater will … attempt to apply its operation to the updated version of the row. The search condition of the command (the WHERE clause) is re-evaluated to see if the updated version of the row still matches the search condition."* *"it is possible for an updating command to see an inconsistent snapshot … This behavior makes Read Committed mode unsuitable for commands that involve complex search conditions; however, it is just right for simpler cases."* Unique constraints: *"Adding a unique constraint will automatically create a unique B-tree index on the column or group of columns listed in the constraint."* *"By default, two null values are not considered equal in this comparison. That means even in the presence of a unique constraint it is possible to store duplicate rows that contain a null value in at least one of the constrained columns."*

**This repository.** **No isolation level is configured anywhere** ⇒ every transaction runs on the PostgreSQL default READ COMMITTED. The lost-update rule is honoured where it matters: `inventory-service/src/main/java/com/shop/inventoryservice/repository/InventoryRepository.java:18-23` reserves stock with a single atomic statement (`SET i.reservedQuantity = i.reservedQuantity + :qty … WHERE … (i.availableQuantity - i.reservedQuantity) >= :qty`) and `:25-29` releases it the same way. Duplicate prevention is delegated to the database: every outbox table has `event_id varchar(36) NOT NULL UNIQUE` (`product-service/.../changelog-001-initial-schema.yaml:174`, `media-service/.../changelog-002-outbox.yaml:9`, `rating-service/.../changelog-001-ratings.yaml:51`, `shipping-service/.../changelog-002-shipping-outbox.yaml:17`, `payment-service/.../changelog-002-payment-outbox.yaml:17`, `order-service/.../changelog-001-initial-schema.yaml:163`), the payment idempotency key has `CREATE UNIQUE INDEX uk_payment_idempotency_key ON payments (idempotency_key)` (`payment-service/.../changelog-001-payments.yaml:37`) and the notification dedup key `CREATE UNIQUE INDEX uk_notification_event_id ON notifications (event_id)` (`notification-service/.../changelog-001-notifications.yaml:40`). Soft deletes use partial unique indexes, e.g. `uk_shipment_order_live … WHERE deleted = false` (`shipping-service/.../changelog-001-shipments.yaml:40`) and `idx_carts_user_active` (`order-service/.../changelog-001-initial-schema.yaml:28`).

**Decision.** Keep READ COMMITTED and do not raise the global level; express concurrency requirements in SQL. Every counter/balance mutation is one atomic `UPDATE` with the guard in the `WHERE` clause; Java-side read-modify-write is forbidden for stock, quantity, balance, retry counters and version columns. Duplicate prevention relies on unique indexes; check-then-insert is forbidden. Because NULLs are distinct by default, any partial unique index whose key column is nullable must exclude NULL explicitly (as `uk_shipments_tracking_live` does at `shipping-service/.../changelog-001-shipments.yaml:84`) and any nullable natural key must get `NULLS NOT DISTINCT` or a filtered index.

**Risks.** A multi-statement transaction can act on a stale row it read earlier — the reason the atomic-`UPDATE` rule exists. A unique constraint over a nullable column silently permits duplicates. Raising the level to SERIALIZABLE would convert races into serialization failures the current retry configuration does not handle.

## 9. `redis-atomicity`

**Official URL** — <https://redis.io/docs/latest/develop/programmability/eval-intro/>
**Version** — Redis **7** documentation, matching `redis:7.4-alpine` (`docker-compose.yml:52`).

**The rule.** *"Redis guarantees the script's atomic execution. While executing the script, all server activities are blocked during its entire runtime. These semantics mean that all of the script's effects either have yet to happen or had already happened."* *"Such scripts can perform conditional updates across multiple keys, possibly combining several different data types atomically."* Determinism: *"the script always must execute the same Redis write commands with the same arguments given the same input data set. Operations performed by the script can't depend on any hidden (non-explicit) information or state … Nor can it depend on any external input from I/O devices. **This repository.** Exactly one Lua script exists, and it is used for the atomic part of the limiter: `gateway-service/src/main/java/com/shop/gateway/ratelimit/RedisEdgeRateLimiter.java:20-48` reads the token count and the last-refill timestamp, computes the refill, decides the allowance and writes both keys back with `SETEX`, executed as a single EVAL at `:70`. The two keys are `gateway:edge-rate-limit:<scope>:<ip>:tokens` and `…:timestamp` (`:67-69`): **no common hash tag**, so the script would fail with CROSSSLOT on Redis Cluster, although the deployment is a single standalone Redis 7.4. Bucket4j is not a dependency.

**Decision.** Any read-modify-write on Redis state is a single Lua script — never GET then SET. Scripts must be deterministic (time and every varying input via `KEYS`/`ARGV`; no `TIME`, `RANDOMKEY`, `SRANDMEMBER`, unseeded PRNG) and must declare every key they touch. The two edge-limiter keys must share a hash tag before any move to Redis Cluster; until then the single-node topology is a documented constraint. Scripts must be loaded by SHA and re-loaded on `NOSCRIPT`.

**Risks.** Splitting the bucket into GET then SET lets concurrent requests each see the same count and both be admitted. The two-key layout breaks under Cluster. Because Redis 7.4 uses effects replication, Redis no longer rejects a non-deterministic script — determinism becomes an application responsibility.

## 11. `stripe-idempotency`

**Official URL** — <https://docs.stripe.com/api/idempotent_requests>
**Version** — Stripe API documentation (current); stripe-java 24.24.0 in this repository.

**The rule.** *"For API v1, Stripe saves the status code and body of the first request made with a given idempotency key after endpoint execution begins. **This repository.** `payment-service/src/main/java/com/shop/paymentservice/provider/StripeProvider.java:66` calls `PaymentIntent.create(params, stripeOptions(idempotencyKey))`, and `stripeOptions` sets `.setIdempotencyKey(idempotencyKey)` at `:199`; the key is also mirrored into the metadata at `:63`. `IdempotencyException` is caught at `:68-71` and reported as an **indeterminate** outcome. **Risks.** A client-supplied key reused for two different payments makes Stripe reject the second request while the local unique index rejects it earlier — the two layers can disagree about which request owns the key. **Decision.** Reusable containers are not used in CI. The deprecated Testcontainers 1.x imports are migrated to the 2.x packages. The Kafka test image must equal the deployed broker image. ## 16. `owasp`

**Official URL** — <https://cheatsheetseries.owasp.org/> — `REST_Security_Cheat_Sheet.html`, `Webhook_Security_Cheat_Sheet.html`, `Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html` (the former `IDOR_Cheat_Sheet.html` now returns **404**), `Secrets_Management_Cheat_Sheet.html`, `Logging_Cheat_Sheet.html`
**Version** — OWASP Cheat Sheet Series, current published revision.

**The rule.** REST: *"Secure REST services must only provide HTTPS endpoints."* *"Passwords, security tokens, and API keys should not appear in the URL."* *"Write audit logs before and after security related events."* Webhook: *"Supply the raw request body before your framework parses it. Re-serializing JSON, reordering fields, changing whitespace or line endings, or converting the character encoding all invalidate the signature (Stripe)."* *"Recompute the HMAC and compare it with a constant-time function such as `hmac.compare_digest`, `crypto.timingSafeEqual`, or `MessageDigest.isEqual`. Never use `==`: it leaks timing information and can turn the endpoint into a signing oracle."* *"Accept only the signature scheme you expect (Stripe's v1, for example) and ignore any other scheme in the header, to prevent downgrade attacks (Stripe)."* *"Return 401 when the signature is missing or does not match, and do not say why."* *"Redact secrets and signature header values from logs and error responses."* IDOR: *"A missing object-level authorization check that allows a user to access or manipulate an object they should not be able to access."* Secrets: *"Many organizations have them hardcoded within the source code in plaintext, littered throughout configuration files."* Logging: data to exclude includes *"Session identification values"*, *"Access tokens"*, *"Sensitive personal data"* and *"Authentication passwords"*.

**This repository.** Webhooks: raw body preserved (`payment-service/.../webhook/PaymentWebhookController.java:33`), SDK verification for Stripe (`payment-service/.../service/WebhookEventService.java:68`), constant-time compare (`payment-service/.../webhook/WebhookSignatureVerifier.java:135`, `:64`), 401 without detail (`utils/common-core/src/main/java/com/shop/common/core/exception/ErrorCode.java:101`), bodies excluded from the HTTP log (`utils/common-spring/src/main/resources/application.yml:72,76`), no token/password value logged (only the token lifetime, e.g. `product-service/.../ServiceTokenProvider.java:100`). Object-level authorization lives in the query: `favourite-service/.../repository/FavouriteRepository.java:18` (`findByIdAndUserId`), `order-service/.../repository/CartRepository.java:21` (`findByIdAndUserIdAndDeletedFalse`), `order-service/.../repository/OrderRepository.java:15`. **Deviations:** the custom verifier falls back to a legacy bare 64-hex HMAC-SHA256 over the body when the header does not start with `t=` (`WebhookSignatureVerifier.java:67-75`) — exactly the downgrade the cheat sheet calls out — and configuration files carry usable secret defaults: `client-secret: ${…:changeme}` at `product-service/src/main/resources/application.yml:58`, `rating-service/src/main/resources/application.yml:43`, `media-service/src/main/resources/application.yml:57`, and `password: ${POSTGRES_PASSWORD:admin}` at `product-service/…:8`, `rating-service/…:8`, `media-service/…:8`, `tax-service/…:8`, `notification-service/…:8`, `shipping-service/…:8`, `payment-service/…:8`.

**Decision.** Only the expected signature scheme is accepted (the legacy bare-HMAC fallback is removed). Constant-time comparison, untouched raw body, 401 without detail, HTTPS with TLS 1.2+. **No secret has a usable default** in a shipped configuration file; the `changeme` and `admin` fallbacks are removed and the properties become mandatory (the payment webhook secret already is: `payment-service/src/main/resources/application.yml:38`). Secrets come from the environment or a secret manager with rotation. Object-level authorization is expressed in the repository query, and each such endpoint has a test that a foreign identifier is refused. Credentials never appear in a URL, a query parameter or a log line. Security-relevant events are audit-logged before and after the action.

**Risks.** The bare-HMAC fallback doubles the verification surface and can mask a broken Stripe configuration. `changeme`/`admin` defaults let a misconfigured deployment start with a well-known credential. Any new repository finder that takes a bare id is a potential IDOR.

## 17. `bucket4j`

**Official URL** — <https://bucket4j.com/> (current documentation **8.22.0**, released 1 Nov 2026; TOC at <http://bucket4j.com/8.22.0/toc.html>, sections 3.1 Concepts, 3.2 Production checklist, 3.5 Bucket4j-Redis)
**Version** — Bucket4j 8.22.0 documentation. **The repository does not depend on Bucket4j** (no `com.bucket4j` artifact in any POM), so this topic evaluates an alternative rather than current code.

**The rule.** *"ProxyManager is the main extension point that connects Bucket4j to a particular storage technology … buckets are distinguished from each other within it by a primary key."* *"BucketProxy is a lightweight handle to a bucket whose actual state is stored outside the current JVM."* Redis: *"concurrent access to Redis is handled via the Compare&Swap pattern"*; *"Bucket4j uses Lua scripts executed atomically via Redis EVAL command to implement the Compare&Swap pattern."* *"Because the entire Lua script is executed atomically by Redis, no other command can run between the compare and swap steps, which guarantees consistency without requiring distributed locks."* *"For the initial bucket creation, a separate SET NX (set-if-not-exists) script is used instead."* Dependency rule: *"The `bucket4j_jdk17-redis` artifact is an aggregator module and should not be used as an application dependency."* Checklist: *"You should expect this and be ready to receive unchecked exceptions when interacting with a distributed bucket."* … *"simply log the exception and continue the business transaction without throttling"* or *"rethrow the exception, or do not catch it at all."* … *"Retention tuning is your responsibility"* (max cache size, expiration policy) … *"High availability (HA) tuning and testing is your responsibility."*

**This repository.** No Bucket4j. The per-route and global limiters use the framework's `RedisRateLimiter` (`gateway-service/.../ratelimit/RateLimitConfiguration.java:15-22,24-30`, applied at `gateway-service/.../config/RoutesConfig.java:38-43`). The edge limiter is the repository's own token bucket as a **single Lua script** (`gateway-service/.../ratelimit/RedisEdgeRateLimiter.java:20-48`, executed as one EVAL at `:70`) — the refill-and-consume decision happens inside a single atomic region, which is the property Bucket4j obtains with its CAS script. The script sets a TTL (`:41-45`), satisfying the expiration requirement, and the key space is per scope and per client IP (the multi-tenant growth the checklist warns about). The current failure behaviour is "log and continue" (`:77-78`) — one of the two behaviours the checklist explicitly allows.

**Decision.** Bucket4j is not adopted: the framework limiter plus the purpose-built Lua script already satisfy the atomic refill-and-consume requirement. If it is ever introduced, the dependency must be `bucket4j_jdk17-redis-common` plus exactly one concrete client module, buckets obtained through a `ProxyManager` with a stable key, and CAS retry limits configured explicitly. The limiter failure policy must be stated explicitly and applied consistently to all three limiters. Key cardinality and expiry must be bounded. The atomic region must cover the whole refill-and-consume decision.

**Risks.** Failing open removes the rate limit entirely during a Redis outage — currently the implemented behaviour, so it must be monitored. A per-client-IP key space grows with the number of clients; only the TTL prevents unbounded growth. Adopting Bucket4j would add a dependency and a second limiter semantic for no functional gain.

## 18. `jvm-performance`

**Official URL** — <https://docs.oracle.com/en/java/javase/25/gctuning/> (HotSpot GC Tuning Guide, **Release 25**, G33936-03, July 2026; `available-collectors.html`, `ergonomics.html`) and the JDK 25 `java(1)` man page <https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html>
**Version** — JDK 25. The repository builds and runs on Java 25 (`pom.xml:34-36`) using `eclipse-temurin:25-jre-alpine` (`product-service/Dockerfile:5`).

**The rule.** Collectors in JDK 25 per the guide: **Serial** (`-XX:+UseSerialGC`), **Parallel** (`-XX:+UseParallelGC`), **Garbage-First G1** (*"G1 is selected by default on most hardware and operating system configurations, or can be explicitly enabled using `-XX:+UseG1GC`"*) and **ZGC** (`-XX:+UseZGC`). *"Unless your application has rather strict pause-time requirements, first run your application and allow the VM to select a collector."* Defaults: *"Garbage-First (G1) Collector on server-class machines, Serial Collector otherwise"*, *"Initial heap size of 1/64 of physical memory"*, *"Maximum heap size of 1/4 of physical memory"*. Container awareness: *"`-XX:-UseContainerSupport` … The VM now provides automatic container detection support … The default for this flag is true, and container support is enabled by default."* *"`-XX:MaxRAMPercentage=percent` … Sets the maximum amount of memory that the JVM may use for the Java heap before applying ergonomics heuristics as a percentage of the maximum amount determined as described in the `-XX:MaxRAM` option. The default value is 25 percent."* *"`-XX:InitialRAMPercentage=percent` … The default value is 1.5625 percent."*

**This repository.** **No JVM option is set for any Java service** — the entry point is a bare `java -jar app.jar` in all **14** service Dockerfiles (`auth-service/Dockerfile:9`, `favourite-service/Dockerfile:9`, `gateway-service/Dockerfile:9`, `inventory-service/Dockerfile:9`, `media-service/Dockerfile:9`, `notification-service/Dockerfile:9`, `order-service/Dockerfile:9`, `payment-service/Dockerfile:9`, `product-service/Dockerfile:9`, `promotion-service/Dockerfile:9`, `rating-service/Dockerfile:9`, `search-service/Dockerfile:9`, `shipping-service/Dockerfile:9`, `tax-service/Dockerfile:9`), and the only JVM flags anywhere are Elasticsearch's (`docker-compose.yml:109`, `ES_JAVA_OPTS=-Xms512m -Xmx512m`). The collector is therefore whatever the VM selects (G1 in these containers) and the heap is whatever the ergonomics produce from the container limit, because container support is on by default. Kubernetes limits are **1024Mi with 512Mi requests** (`k8s/microservices.yaml:30,33`, repeated at `:89,92` and `:148,151`; `k8s/gateway-service.yaml:39,42`), so the documented default `MaxRAMPercentage` of 25 % caps the heap at roughly **256 MiB** of a 1 GiB container. Nothing sets `-XX:MaxRAMPercentage`, `-Xmx`, `-XX:+UseG1GC` or `-Xlog:gc*`, and no GC metric is exported.

**Decision.** The collector is not chosen explicitly — the documented default selection is kept (G1), and `-XX:+UseSerialGC`/`-XX:+UseParallelGC`/`-XX:+UseZGC` are not used without a measurement. Because container support is on by default, the heap must be sized explicitly: **`-XX:MaxRAMPercentage=75`** plus an explicit `-XX:InitialRAMPercentage` in every service entry point, with the container limit and the percentage changed together. GC observability is enabled (`-Xlog:gc*`, sized so it cannot fill the container disk) and a GC-pause metric is exported. The pause-time goal is only set if measurement justifies it.

**Risks.** Leaving the heap at the 25 % default inside a 1 GiB container leaves ~256 MiB for a service with a 20-connection Hikari pool, Netty/Tomcat threads and Jackson buffers — full GCs and `OutOfMemoryError` before the container limit is reached. Raising the percentage without raising the limit converts heap exhaustion into an OOM kill, which is harder to diagnose. Without GC logging, a pause-time regression is invisible in the exported metrics.

## 19. `observability`

**Official URL** — <https://docs.spring.io/spring-boot/reference/actuator/> → `actuator/endpoints.html`, `actuator/metrics.html`
**Version** — Spring Boot **4.1.x** reference (the unversioned path serves 4.1.2 and redirects `/spring-boot/4.1/...` to it). The project pins 4.1.1 (`pom.xml:9-12`).

**The rule.** *"By default, only the health endpoint is exposed over HTTP and JMX."* *"Since Endpoints may contain sensitive information, you should carefully consider when to expose them."* *"The include property lists the IDs of the endpoints that are exposed. The exclude property lists the IDs of the endpoints that should not be exposed. The exclude property takes precedence over the include property."* Details: *"The information exposed by the health endpoint depends on the `management.endpoint.health.show-details` and `management.endpoint.health.show-components` properties."* Probes: *"`livenessstate` — Exposes the 'Liveness' application availability state."*, *"`readinessstate` — Exposes the 'Readiness' application availability state."*, *"These can be disabled by using the `management.endpoint.health.probes.enabled` configuration property."* Groups: *"You can also override the show-details and roles properties if required"* (e.g. `management.endpoint.health.group.custom.show-details=when-authorized`, `…roles=admin`).

**This repository.** Shared actuator configuration at `utils/common-spring/src/main/resources/application.yml:32-56`: exposure include `health,info,prometheus,metrics` (`:36`), `show-details: when-authorized` (`:39`), `probes.enabled: true` (`:41`), `prometheus.access: read_only` (`:42-43`), liveness/readiness state indicators enabled (`:44-48`). Business metrics are exported through Micrometer (`product-service/src/main/java/com/shop/productservice/service/ProductMetrics.java:25-38`) and the resilience4j metrics land on the metrics endpoint automatically. The gateway uses a narrower set (`gateway-service/src/main/resources/application.yml:83-98`: `health,info,prometheus`). On the path level the common security configuration permits `/actuator/health`, `/actuator/health/**`, `/actuator/info` **and `/actuator/prometheus`** without authentication (`utils/common-security/src/main/java/com/shop/common/security/config/SecurityProperties.java:84-87`), while `/actuator/metrics` is **not** in that list and therefore requires an authenticated principal. The gateway routes `/actuator/health`, `/actuator/health/**` and `/actuator/info` publicly (`gateway-service/src/main/resources/application.yml:37-40`). **No management port is configured anywhere**, so the actuator shares the application port.

**Decision.** The actuator is exposed on the application port, so path-level rules are the only barrier: the health endpoint is public (aggregate status only, because `show-details=when-authorized`), the Prometheus scrape endpoint is reachable only from the monitoring network, and `/actuator/metrics` stays authenticated. Because the Prometheus endpoint publishes the same measurement data that the authenticated metrics endpoint protects, `/actuator/prometheus` is removed from the public path list or the actuator is moved to a dedicated `management.server.port`. `env`, `beans`, `configprops`, `loggers`, `heapdump`, `threaddump`, `scheduledtasks` and `shutdown` are never added to the include list, and the exclude list is used as a second barrier because *"the exclude property takes precedence over the include property"*. The Kubernetes probes use the documented `LivenessStateHealthIndicator`/`ReadinessStateHealthIndicator` with `probes.enabled=true`, and the readiness probe must reflect the ability to serve traffic (Kafka consumer and outbox relay running), not only the application availability state. The custom business metrics remain the primary observability surface.

**Risks.** Exposing `/actuator/prometheus` on the public path publishes exactly the data the authenticated metrics endpoint protects — metric names, tags and values revealing internal service names, URI templates and error counters. With no separate management port the actuator inherits every exposure mistake of the application. A readiness probe that only reports the application availability state reports UP while the Kafka consumer is stopped, so traffic keeps being routed to a service that cannot process it.
