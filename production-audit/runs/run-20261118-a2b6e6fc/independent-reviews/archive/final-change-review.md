## 4. What I could NOT verify, and why

1. **The reactor build itself.** I was instructed not to start Maven builds (the lead is running one and we would contend for the host). I therefore rely on the harness's own record: `suites.build = PASS, exit_code 0, duration 1237.992s, fingerprint bf4eec9d03be…` matching the current working tree, log at `production-audit/runs/run-20261118-a2b6e6fc/test-results/build-verify.log`. I did not read that log line by line, and I did not re-run the build. Every Java-level claim in this review is from **reading the source**, not from executing it.
2. **The Java integration tests** (*IT) — they need Docker/Testcontainers and a full Maven run; I did not execute them. The concurrency, idempotency and outbox findings (D-07, D-08, D-16…D-19) are therefore *source-level* findings: I proved that the assertions are weak or the semantics changed, not that a test fails.
3. **Whether the shared `application.yml` is shadowed or merely overridden** (D-22). I proved the **observable** consequence — the shared `management.*` settings are not in effect in the running fleet — by direct observation of the published series and of the raw scrape. The *mechanism* (classpath shadowing of `classpath:/application.yml` by the per-service copies) is the most likely cause but I did not prove it with a JVM-level experiment, and I did not rule out a different cause (e.g. a Micrometer/OTel setup that drops common tags). The consequence is proven; the cause is inferred.
4. **Real Telegram delivery.** No bot credentials exist in this environment (ALT-07 = BLOCKED: bot token present False, chat identifier present False). I could not exercise the runtime delivery path; my D-05 finding is from reading `scripts/notify-telegram.sh`, not from executing it against the API.
5. **Real Stripe sandbox E2E.** No valid `sk_test_` credential is configured (the committed report §12 records the Stripe API rejecting the key: "Invalid API Key provided: sk_test_…j9k0"). I verified the harness's *classification and status logic* only. I did not and could not confirm a genuine payment-intent round trip.
6. **Kubernetes behaviour.** No reachable cluster exists (`harness k8s` non-validate actions return BLOCKED by design). I verified the manifests statically: kubeconform schema validation and the harness's own 13 structural checks. I did not exercise HPA/KEDA scaling, PDB eviction behaviour, `runAsNonRoot: true` with `runAsUser: 1001` against the actual container images, or the `ServiceAccount`/`automountServiceAccountToken` wiring — all unverified.
7. **The PostgreSQL exporter's silence** (D-04). I proved the exporter is up and publishes zero `pg_*` series. I did not inspect the exporter's logs or its `DATA_SOURCE_NAME` resolution, so I cannot say whether the exporter is failing to connect, running a reduced collector set, or being scraped with a wrong path. The defect stands either way: the rule cannot fire.
8. **The Prometheus `namespace` label** (D-11). I proved `prometheus.yml` has no `relabel_configs` and that no series carries a `namespace` label. I did not check whether a Kubernetes-side Prometheus Operator adds it, because there is no cluster and the compose Prometheus is the one in scope.
9. **Load-test behaviour under real load.** I did not start k6 (the lead's instruction forbids new containers). The two recorded runs under `production-audit/runs/run-20261118-a2b6e6fc/load-results/` are `baseline` only. No `spike`, `flash-sale`, `promotion-storm`, `soak` or `failure-during-peak` evidence exists, so the claims in report §19/§23/§24/§25 have no measured basis at all.
10. **Kafka ordering under concurrency.** I proved the claim-selection change (D-16) from the SQL and the repository diff. I did not run two relay instances against a real broker to observe a cross-instance ordering violation; the finding is that the ordering guarantee is no longer established by the implementation, not that a violation was observed.
